# v2.0.0

- **Released:** 2026-04-22
- **Summary:** Release-anchored upgrades, migration consolidation, and a large batch of organization/admin/extension improvements.

## Upgrade Notes

### 1. `core-update.sh` now targets release tags, not `master`

Previously, `scripts/_core/core-update.sh` always cloned upstream `master`. Two problems:

- Sub-apps pulled in-flight changes between releases.
- `--list-divergences` flagged every file that moved on master since the last upgrade, even when the sub-app hadn't changed anything.

From v2.0.0:

- A normal upgrade (no flag or `--analyze`) targets the **highest `vX.Y.Z` tag** on the upstream remote.
- `--list-divergences` targets the **tag matching the locally recorded version** (`.starterpack-version`). Divergence now means "I customized core files past the release I'm on," not "I'm behind on upstream master."
- If the required tag isn't on the remote, the script fails loudly rather than silently falling back to master.

Implication for releases: the git tag is load-bearing. The `release-starterpack` skill now creates and pushes the tag from CLI before the GitHub release step.

### 2. Migrations consolidated into a baseline file

The nine pre-v2.0.0 migrations are replaced by a single file:

```
app/backend/migrations/2026-04-21-v1.4.0-baseline.sql
```

It is the concatenation of those nine files in date order, so the schema it produces is identical byte-for-byte to running them individually.

Sub-app impact:

- **Existing sub-apps on v1.x**: the baseline appears on disk and your database is already migrated, so the baseline is a no-op (`IF NOT EXISTS` guards throughout). **One manual step required** — see "Post-upgrade cleanup" below.
- **Fresh installs**: run the baseline once, like any other migration.

### Post-upgrade cleanup (one-time, for sub-apps upgrading from v1.x)

The pre-v2.0.0 `core-update.sh` has a gap: when a release both removes files from the manifest **and** deletes them upstream in the same release, the old files are orphaned on disk instead of being cleaned up. The v2.0.0 script fixes this, but the upgrade *to* v2.0.0 runs the old script, so the 9 consolidated migration files will be left behind.

After the upgrade completes, delete them:

```bash
cd app/backend/migrations && rm -f \
  2026-01-06-soft-delete-users.sql \
  2026-01-09-organizations.sql \
  2026-01-14-oauth-provider.sql \
  2026-01-16-conversations.sql \
  2026-01-19-org-metadata.sql \
  2026-04-16-conversation-subtype.sql \
  2026-04-20-org-invitations.sql \
  2026-04-21-organization-billing.sql \
  2026-04-21-user-metadata.sql
```

This only applies to the v1.x → v2.0.0 upgrade; later releases use the patched script and won't leave orphans.

### 3. New migration naming: `YYYY-MM-DD-vNEXT-description.sql`

Author new migrations with the `vNEXT` placeholder. The `release-starterpack` skill rewrites `vNEXT` to the actual release version (`vX.Y.Z`) when cutting the release, and fails loudly if any `vNEXT` file is left over.

This is documented in `CLAUDE.md` and `app/backend/migrations/README.md`.

## New Features

### Organization UX overhaul

- **Role rename (UI only):** organization "Admin" is now "Owner" in the UI. The DB column name is unchanged.
- **`/account` hub:** Organizations and Billing are now tabs under `/account`. `/premium` redirects to `/account?tab=billing`.
- **Org detail page** split into Overview | Members | Billing | Settings tabs. Members tab is visible to any org member (non-owners see roster with no controls).
- **Quota bar + alerts:** persistent `UProgress` quota bar and a self-last-owner alert.
- **Member actions:** icon cluster replaced with a labelled `UDropdownMenu`.
- **Billing tab** hides itself for owners when self-service subscriptions are disabled.
- **Premium source** collapsed from four conditional strings to one "Source:" line.

### Email invitations (behind new feature flag)

- New env var `ORG_INVITATIONS_ENABLED` (**off by default**) gates an email-based invitation flow for organizations. Leave it off and the old invite path keeps working.

### Admin-managed billing for bank-transfer orgs

System admins can assign plans, record payments, and run a daily cycle debit against Stripe `customer.balance` without creating real Stripe subscriptions. The admin UI uses intuitive signs: positive = credit, negative = owed (flipped at the Stripe boundary).

### User `custom_data` extension point

Mirrors the existing organization `custom_data` pattern. Adds a JSONB column to users, plus `UserCustomData` and `UserPreviewCustomData` templates in `schemas/user_ext.py` for privacy-safe previews. Sub-apps extend users without touching core schemas; TS types are auto-generated via `convert-models`. Frontend gets matching template components for profile edit, admin user page, and signup form.

### Conversation `subtype` field

Optional, immutable `subtype` column on conversations for app-specific classification (e.g. `organization_request`). Backend model/schema/CRUD/controller wiring is in place; admin UI gets a filter dropdown driven by a configurable `conversation-subtypes-ext.ts`.

### Overridable `PageActions`

The header action buttons on the Organizations and Messages pages are now overridable via `config/component-overrides.ts`, so sub-apps can swap them without modifying core files.

### Admin improvements

- Events page: organization and conversation filter dropdowns.
- Admin can create conversations.
- User detail page: tabbed layout with an Org Memberships tab.
- New `AdminPageBanner` component (9 admin headers DRY'd up, red "Admin" badge).

### Dev UX

- `npm run dev` and `npm run start` now print a post-startup banner with app/API/Adminer/analytics URLs and which feature flags are on. `npm run info` reprints it.
- New `db-migrate.sh` helper to apply migration files.

### `core-update.sh --list-divergences` flag

Read-only audit that surfaces core files diverging from the release recorded in `.starterpack-version`: template-mode files (intentionally customized, but upstream may have evolved) and sync-mode files (unexpected drift). Exits 1 if any divergence is found.

## Bug Fixes

- Organization `custom_data` is now persisted on create/update. It was previously accepted by the schema but silently dropped. PATCH now merges rather than replaces to preserve unrelated keys.
- No more duplicate participant when a system admin is also an admin of the org.
- Checkout redirect URL now matches the user role.
