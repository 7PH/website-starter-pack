# v3.8.1

- **Released:** 2026-06-14
- **Summary:** Test-only patch. The `custom_data` privesc regression test added in v3.8.0 over-asserted and failed for any sub-app that adds fields to `UserCustomDataWritable`; it now checks the actual security property and is a stronger guard.

## Upgrade Notes

**No action required.** No schema, API, migration, or runtime changes — only `tests/test_custom_data_privesc.py` changed. Sub-apps on v3.8.0 that added self-writable fields (the intended extension) saw `test_undeclared_field_is_dropped_on_self_write` fail; upgrading clears it.

## Bug Fixes

### `custom_data` privesc test failed for sub-apps with writable fields

`test_undeclared_field_is_dropped_on_self_write` asserted `parsed.custom_data.model_dump() == {}`, which only holds when `UserCustomDataWritable` is empty (the baseline). A sub-app that added a self-writable field (e.g. `username_custom`) made the dump non-empty by design, so the test failed even though the injected privileged key was correctly dropped.

The assertion now checks that **no key outside the writable set survives** — `set(parsed.custom_data.model_dump()) <= set(UserCustomDataWritable.model_fields)` — and the payload now injects `is_mod` (privileged-on-full) alongside `is_admin` (undeclared). This:

- passes on the empty baseline (`set() <= set()`) and on sub-apps that add writable fields, and
- is a **stronger** guard: it now fails if a self-write schema ever regressed to the full `UserCustomData` (the previous `== {}` / single-key check could not catch that, since the injected `is_admin` is not a field on the full type either).
