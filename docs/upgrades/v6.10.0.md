# v6.10.0

- **Released:** 2026-11-27
- **Summary:** Security hardening of sessions, invitations and Google sign-in, and organizations may share an email. Two migrations to run.

## Security

- **Sessions can be revoked.** Every token carries the user's `token_version`, checked against the DB on each request. Changing or resetting a password, deleting the account and removing someone's admin rights sign them out everywhere. An impersonation token stops working once its admin loses admin rights
- **The DB decides `is_admin`, `email` and `email_confirmed`**: `get_current_user` now reads the user row (one primary-key lookup) instead of trusting the token claims
- **Password reset links work once**
- **Tokens last 7 days** instead of 30. They still slide: the app refreshes them, so active users stay signed in
- **Deleted accounts lose their organization memberships**
- **Invitations need a confirmed email.** An unconfirmed account sees no pending invitations and cannot accept or decline one. Sending an invitation also needs a confirmed email
- **Invitation sending is limited**: 20 per user and 50 per organization per day, at most 50 pending per organization, and pending invitations count toward `ORG_MAX_MEMBERS`
- **Google sign-in refuses an email Google has not verified**, for both sign-up and linking to an existing account

## Upgrade Notes

**Run both migrations**, before deploying the new backend (it reads `users.token_version` on every request):

- `2026-11-27-v6.10.0-user-token-version.sql` adds `users.token_version`
- `2026-11-27-v6.10.0-org-email-not-unique.sql` drops the unique constraint on `organizations.email`

Existing sessions stay valid after the upgrade. Things to check in your app:

- `create_access_token` takes a required `token_version=` (the DB value for the user the token represents). Prefer `issue_jwt_with_orgs` / `issue_jwt_for_user`, which pass it for you
- `create_password_reset_token(user_id, token_version)` takes the user's `token_version`
- `PUT /users/me/password` returns a `UserTokenUpdate` (a fresh token for this session) instead of a `UserRead`. The core frontend saves it. Code that bumps `token_version` itself should call `revoke_sessions(user)` and hand the user a new token
- `get_current_user` is now a sync dependency that uses the DB session. Code that `await`s it breaks, tests that called it directly need a session, tests that override it are unaffected
- `GoogleUserInfo` gains `verified_email` (default `False`): code or tests that build one themselves must set it, or the sign-in is refused
- The frontend handles a refused token with `auth.dropRefusedToken()`: it switches to a newer token another tab stored (eg after a password change) and only logs out without one. Use it instead of `logout()` in your own 401 handlers
- `get_organization_by_email` and `is_org_email_taken` are removed
- Without a mail service, password users cannot confirm their email, so they cannot use invitations. Seed them confirmed (`PREVIEW_SEED_USERS`) or set `email_confirmed` in SQL
