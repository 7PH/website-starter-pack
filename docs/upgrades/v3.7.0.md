# v3.7.0

- **Released:** 2026-05-29
- **Summary:** Three things: a CI rebuild that halves the workflow job count and adds Docker layer caching, a second-pass backend hardening pass (perf indexes, batched N+1 queries, race fixes, deprecated shim removal), and a prod nginx build fix that stops `/_nuxt/*.js` from 404ing when `SITEMAP_ENABLED` differs from the default.

## Upgrade Notes

**Non-breaking for most sub-apps.** Two things need attention:

1. **One new migration** — `2026-05-16-v3.7.0-perf-indexes.sql`. Adds two indexes (`idx_users_stripe_id`, `idx_messages_conv_created`). Idempotent (`CREATE INDEX IF NOT EXISTS`), safe to re-run.
2. **Removed deprecated helpers** — if your sub-app still imports any of these, switch to the event-bus equivalent before upgrading (see below).

### Removed deprecated helpers

These were deprecated shims kept for backward compatibility and are now gone:

- `register_code_validator(fn)` in `helpers/auth.py` → use `@on(AccessCodeResolution)` from `helpers/hooks.py`.
- `set_group_management_policy(fn)` in `helpers/policies.py` → use `@on(GroupManagementCheck)` from `helpers/hooks.py`.
- `send_welcome_email(to_email, username)` in `helpers/email.py` → removed; no replacement (was unused in core).

If you don't import these, nothing to do.

### CI: branch protection check names changed

`/upgrade-starterpack` removes the old workflow files (`lint.yml`, `typecheck.yml`, `unit-tests.yml`) because `core-update.sh` deletes core files no longer in `starter-pack-files.txt`. If your sub-app has branch protection pinned to the old check names, repoint them to `Frontend Checks` and `Backend Checks` after upgrading or PRs won't be mergeable.

### Optional: route CI to a self-hosted runner

Set the `CI_RUNNER_LABEL` repo variable to a runner label and every workflow except `preview.yml` runs there instead of `ubuntu-latest`:

```
gh variable set CI_RUNNER_LABEL --body "preview-host"   # or whatever your runner label is
```

The `self-hosted` part is added automatically — you only set your custom label. Unset to fall back to `ubuntu-latest`. If jobs sit in "Waiting for runner", the label likely doesn't match any online runner (check `Settings → Actions → Runners`).

### Migration

Run `2026-05-16-v3.7.0-perf-indexes.sql`.

## Bug Fixes

### `SITEMAP_ENABLED` build-arg parity (prod nginx)

`Dockerfile.prod-nginx` didn't receive the `SITEMAP_ENABLED` build arg, so when it differed from the default the nginx asset build and the SSR node build produced different `_nuxt/*` hashes — every `/_nuxt/*.js` 404'd in production. The arg is now passed to both builds from `docker-compose.core.yml`, keeping the hashes in sync.

### Backend hardening (second pass)

- **N+1 batching** — conversation listing, organization member/invitation listing, and managed-account-group lookups now batch their queries instead of one-per-row.
- **Race fixes** — Stripe premium application and billing tasks tightened against concurrent updates.
- **Perf indexes** — see migration above (`idx_users_stripe_id` for Stripe webhook user lookups, `idx_messages_conv_created` for conversation message ordering).
- **i18n trim** — `core-en.json` / `core-fr.json` dropped ~90 lines of unused keys each.

## New Features

### `CI_RUNNER_LABEL` repo variable

Optional GitHub Actions repo variable. When set, every workflow except `preview.yml` runs on a runner with that label instead of `ubuntu-latest`. Unset → existing behavior. No sub-app code change required to adopt or revert.

### GHA Docker layer cache

`build.yml` and `e2e.yml` use `docker/setup-buildx-action@v3` and write a `docker-bake.override.hcl` mapping each known core build target to its own GHA cache scope. With `COMPOSE_BAKE=true`, `docker compose build` delegates to `buildx bake` and respects the cache config. Sub-apps that add their own prod services build those without cache unless they extend `docker-bake.override.hcl` with a target block per build.

### Concurrency cancel-in-progress (PR only)

Each workflow groups by `${{ github.workflow }}-${{ github.ref }}` and cancels superseded runs **only when the trigger is `pull_request`**. Master-push runs always complete, so direct-to-master releases never lose validation mid-flight.
