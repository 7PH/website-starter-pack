# v3.8.0

- **Released:** 2026-06-14
- **Summary:** Two things: a privilege-escalation guardrail on `user.custom_data` (a new `UserCustomDataWritable` type so users can only self-set non-privileged fields), and a frontend duplication cleanup that pulls two repeated blocks into shared composables.

## Upgrade Notes

**Action required for every sub-app** — one manual edit to `app/backend/src/schemas/user_ext.py`, plus a frontend type regen.

### Required: add `UserCustomDataWritable` to `user_ext.py`

`user_ext.py` is a template (app-owned, not synced), so the upgrade won't touch your copy. But the synced core `schemas/user.py` now imports `UserCustomDataWritable` from it. Without the class, the backend fails to start with `ImportError`.

Add the writable base and have `UserCustomData` extend it:

```python
class UserCustomDataWritable(BaseModel):
    """Fields a user may set on THEMSELVES (signup + /account profile edit)."""
    # move self-writable fields here
    pass


class UserCustomData(UserCustomDataWritable):
    """Full shape (reads + admin writes). Privileged fields go here only."""
    # keep privileged/admin-only fields here
    pass
```

If your sub-app added fields to `UserCustomData` that users were meant to set on their own account, **move them into `UserCustomDataWritable`** — otherwise they'll be silently dropped from signup (`POST /users`) and profile-edit (`update_me`) payloads. Privileged fields (roles, entitlements, credits, internal flags) stay on `UserCustomData`: that is the guardrail. A field only reachable on the full type can no longer be self-granted by a user POSTing it.

### Required: regenerate frontend types

After the `user_ext.py` edit, run `./scripts/_core/convert-models.sh` so `types/models.ts` picks up `UserCustomDataWritable` and the new `UserCreate` / `UserChangeInfo` field types.

### No migration

No database changes in this release.

## Security

### Privilege escalation through `custom_data`

`user.custom_data` (JSONB, extended per-app via `UserCustomData`) used the same type on reads and on user-controlled writes. A sub-app that added a privileged field to `UserCustomData` let a regular user grant it to themselves by including it in their own create/update payload.

The fix splits the type: `UserCreate` and `UserChangeInfo` now accept only `UserCustomDataWritable`, while reads and the admin write path (`update_user_by_admin`) keep the full `UserCustomData`. Pydantic drops undeclared keys by default, so any field not on the writable type is stripped at the API boundary before storage.

Baseline impact is nil (the baseline schema is empty); this is a safe-by-default structure sub-apps inherit. Covered by `tests/test_custom_data_privesc.py`.

## Bug Fixes

### `custom_data` datetime serialization (JSONB)

`update_me` and `update_user_by_admin` rebuilt `custom_data` with `model_dump(exclude_none=True)`, which leaves `datetime` fields as Python objects that the JSONB write can't serialize. Both now use `model_dump(mode="json", ...)` so datetimes store as ISO strings.

## New Core Files

- `app/backend/tests/test_custom_data_privesc.py` — regression tests for the write/read type split.
- `app/frontend/composables/useShareLink.ts` — builds the `/c/<token>` managed-account share URL and copies it to the clipboard. Shared by the managed-account-groups list and detail pages.
- `app/frontend/composables/organizations/useOrganizationQuotaDisplay.ts` — derives the seat-usage display (color, used/total, progress value) for an organization. Shared by `BillingTab` and `MembersCard`.

## New Features

### `useShareLink()` composable

Auto-imported. Returns `shareUrl(token)` and `copyShareLink(token)` (clipboard copy + success/error toast). Use it anywhere you surface a managed-account share link.

### `useOrganizationQuotaDisplay(orgRef)` composable

Wraps `useOrganizationQuota` and returns `quotaState`, `isOverQuota`, `progressColor`, `usedSeats`, `totalSeats`, and `progressValue` for rendering org seat-usage UI without re-deriving the math.
